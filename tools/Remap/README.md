# Remap：混淆名映射重建

游戏用 GUPS 混淆，每次更新混淆名（`yb`、`bbe.kqi`、`k896ff…`）都会全部改变。DBModKit 是唯一直接引用游戏代码的项目，
这个工具把它源码里的旧名字对应到新版，其他 Mod 不用动。

```powershell
dotnet build tools/Remap -c Release
$remap = "tools/Remap/bin/Release/net8.0/Remap.dll"
dotnet $remap update --old ../backup/7.11                 # 只检查，报告在 tools/Remap/out/report.md
dotnet $remap update --old ../backup/7.11 --write         # 写回 DBModKit 源码
dotnet $remap snapshot --version 7.12                                   # 适配完新版本后保存，作为下次的 --old
dotnet $remap selftest --old ../backup/7.11 --mutate 0.03 # 自测
```
`dotnet $remap help` 查看全部选项。`--notes ../tools/NOTES.md` 会同时改笔记里反引号中的 `类型.成员`。

## 原理
处理 DBModKit 引用的三个会被混淆的程序集：Assembly-CSharp、Mirror、com.rlabrecque.steamworks.net。

1. **对应**（`Matcher`）：旧版每个类型、方法、字段、属性、事件找新版里的同一个。
   - 锚点：不像混淆名的名字（`ActiveSkillData`、`heroType`、Unity 消息方法）同名即对应；P/Invoke 入口名；事件和同名的后备字段。
   - 打分：解密后的字符串常量、外部调用（Unity、mscorlib）、数字常量、指令分布、签名，以及"引用了 / 被谁引用了哪些已对应的成员"。只接受双方互为最优、领先次优足够多的配对，先严后宽。
   - 传播：已对应的两个方法按指令顺序对齐各自引用的成员，同一位置上还没对应的成员就是一对（所有投票一致才接受）。
   - 等价副本：混淆器的诱饵里有逐字节相同、又都没人调用的方法（如 `cft.tqi` / `cft.kcv`），实在分不出时按顺序配对，报告里标 ⚠。
2. **改写**（`SourceScan`）：用 Roslyn 按旧版编译源码，找出所有绑定到游戏成员的标识符、命名参数，
   `Compat.cs` 清单和 `AccessTools.Method(typeof(X), "名字")` 里的字符串，以及注释里的 `类型.成员`，换成新名字。
   还会改 Harmony 补丁的 `___字段` 参数（按字段名在整个程序集里找，唯一时才改）和 `"<属性>k__BackingField"`（跟着上下文类型的属性改）。
   字符串只在参数位置（或作为参数传入的数组里）才当成类型名，字段里的普通字符串数组（语言代码 `"ja"`、`"it"`）即使和混淆类型同名也不改。
3. **检查**：改写后的源码按新版程序集再编译一遍（引用和 `Directory.Build.props` 一致），报告错误。

## 结果怎么看
- 报告"需要人工处理"：没有对应的成员、编译错误。代码里缺对应的标识符保持原样，编译会在那里报错。
- 标 ⚠ 的：分数领先不多，或是等价副本。如果是 Harmony 补丁的目标，要对照反编译代码确认补丁打在被调用的那一个上（诱饵没有调用者）。
- "提示"里的字符串（`"hp"`、`"cost"` 等反射用的字段名、表格列名）工具找不到所属类型，只有新版里同名成员真的改了名才列出，需要人工确认。

## 自测
`selftest` 把旧版随机重新混淆一遍（改名、打乱顺序、随机改动一部分方法的常量），用标准答案检查准确率，再检查 DBModKit 改写后能否编译。
在 6.45 上（3 个种子各改动 3% 的方法，另测 1 个种子改动 10%）：DBModKit 用到的 346 个成员全部正确，改写后编译 0 错误；
整个程序集 0 错配（代码相同、没人调用的诱饵副本互换单独统计），约 9.5% 的成员没有对应（多是没人引用、又被改动过的），会如实列在报告里。

局限：模拟改名不等于真实更新。真实更新还可能增删大量代码、换字符串加密方式（`Side.DecryptStrings` 读不出时会警告）。
所以每次仍要看报告、编译、实机测试后再发版。

**第一次真实更新（6.45 → 7.01，2026-10-24）**：对应上 71.7% 的成员，DBModKit 改名 1936 处，只有 Steam 大厅成员数据的两个包装方法
（`cgk.ubm` / `cgk.ubl`，游戏自己不调用）没对应，要对照反编译代码手动补。

**7.01 → 7.02（2026-10-24）**：大部分混淆名没变，对应上 72.0%，DBModKit 改名 735 处；还是只有 `cgk` 的大厅成员数据包装方法要手动补（新版同类里有多个逐字节相同的副本，按 P/Invoke 入口核对后任选一个）。
报告里的"重载对应到不同的名字"是同名的另一个重载被删了，实际用到的重载名字没变，可以忽略。

**7.02 → 7.03（2026-10-24）**：这次又全部重新混淆了，DBModKit 改名 1813 处。手动补：`che` 的大厅成员数据读取方法；类型改名后 Compat 里写成字符串的类型名（`"bbr"` → `"bbs"`，因为旧的 `yh` 里恰好有同名成员，工具不敢改）；`ez.dyq` → `dzk`（工具报"重载对应到不同的名字"，但映射本身是确定的，按报告表格里的对应改）。

**7.03 → 7.06（2026-10-26，跳过了 7.04、7.05）**：改名 1923 处。新坑：混淆器给 `ym`（角色）的一个方法也取名 `hp`，和 `hp` 字段撞名，C# 里 `.hp` 会解析成方法组，编译报 CS0428 / CS0019——改用 `AccessTools.FieldRefAccess<ym, long>("hp")`（`GameRaw.Hp`）。以后遇到"方法组"类的编译错误，先查是不是字段和方法同名。其余手动补：`chq` 大厅成员数据读写（uig/uih）、Compat 里的 `"ivx"` → `"ixb"`、Hooks 里的 `"dzq"` → `"eac"`。

**7.06 → 7.10（2026-10-30，跳过了 7.07–7.09）**：改名 1968 处。这次有几个方法改了签名，工具对应不上（报"没有对应"）：伤害结算 `ez.dzr` 末尾加了 `AttackType? k`（只影响伤害数字的显示类型）→ `ey.eae`；技能工厂 `ez.eba` 末尾加了 `Quaternion? j`（朝向覆盖）→ `ey.ebn`，Harmony 的参数类型数组要补上 `typeof(Quaternion?)`；炸弹初始化 `bif.nez` → `bii.niw`（签名没变，但诱饵副本太像）；大厅成员数据读取 `chq.uig` → `chv.umv`（逐字节相同的副本任选一个）。做法：反编译新版，按签名找候选，数调用次数——诱饵副本没有调用者，真的那个有（`ey.eae` 189 处）。

**7.10 → 7.11（2026-10-30）**：作者修 bug 的小更新，没有全部重新混淆，改名 665 处。只有大厅成员数据读取 `chv.umv` → `chv.umw` 要手动补；报告里 `yl.lbz` 的"重载对应到不同的名字"可以忽略（用到的是 `bbx.lbz(rv)`），字符串 `"cd"` 是表格列名，不用改。
